# M12.8 — PublicationFamily and RecruitmentCampaign persistence foundation

Baseline: `19d9f98eba1996a9a41b894f5c2fc8b22fd2ab76`. Working tree was clean at entry. No commit created. The existing local application database was not opened or migrated during this work; migration 8 is registered for normal database startup. Tests exercised temporary/in-memory databases.

## Documented architecture and resolved ambiguities

DATA_MODEL sections 32–37, 63–64, PRODUCT_SPECIFICATION sections 13–14, and ARCHITECTURE distinguish observations, publication families, recruitment campaigns and employer clusters. PublicationFamilyMembership references SourceObservation. RecruitmentCampaignMembership references a family or an observation, with family preferred. EmployerCluster has many RecruitmentCampaigns. CanonicalVacancy is not a membership target.

The initial milestone's canonical-vacancy membership proposal conflicted with those documents. Implementation waited for explicit approval to follow the documented layers. The further unspecified cardinality and target rules were resolved by the user:

- At most one active family per observation; many observations per family; no family is valid.
- Multiple active campaigns per family or family-less observation; no exclusive campaign ownership.
- Exactly one campaign target: family XOR observation.
- New direct observation decisions are rejected when an active family exists.
- Joining a family does not rewrite, delete or supersede existing direct campaign decisions.

DATA_MODEL.md and PRODUCT_SPECIFICATION.md were not revised. No further architectural contradiction was found.

## Domain fields

PublicationFamily retains id, createdAt, updatedAt and optional representativeTitle.

RecruitmentCampaign retains id, required employerClusterId, the documented ACTIVE / PROBABLY_ACTIVE / ENDED / RECURRENT / UNKNOWN status, firstObservedAt, lastObservedAt, createdAt and updatedAt. Optional occupation is a typed descriptive snapshot with id/canonicalName and optional classification system/code. Location reuses the existing VacancyLocation value type without introducing canonical membership. Position count encodes the documented count and count type together as a discriminated value: EXACT or MINIMUM with value, RANGE with minimum/maximum, PLURAL_UNKNOWN or UNKNOWN without invented numbers. These descriptive values are JSON columns, not new occupation/location identity tables. No status, dates or descriptive values are inferred by the repositories.

Both membership types retain id, target/owner IDs, confidence, status, algorithm, algorithmVersion and evaluatedAt. createdAt, explicit sourceType (USER_CONFIRMED / SYSTEM_MANUAL / TEST_FIXTURE), optional explanation, and optional supersededAt provide recording provenance and auditable lifecycle. No opaque automatic provenance or matching service was introduced. Caller-supplied algorithm/version identify the explicit decision procedure; they do not execute inference.

## Active state, lifecycle and conflicts

The existing observation-cluster status vocabulary is reused: PROPOSED, ACCEPTED, REJECTED, USER_CONFIRMED. Active means ACCEPTED or USER_CONFIRMED and not superseded. Proposals/rejections remain audit records, not effective ownership. This follows the existing recognition convention rather than adding a second status model.

Entity save is create-only; duplicate IDs conflict. Returned/stored values are defensively copied. Membership decisions cannot be edited or hard-deleted through these repositories. SQLite additionally prevents decision mutation/deletion with triggers. supersedeMembership ends a decision explicitly while preserving all original fields. Its timestamp cannot precede evaluatedAt or createdAt. Repeating the same supersession is idempotent; trying to change its timestamp fails. A new decision can follow supersession, and has its own provenance and ID. No automatic replacement, reassignment or reconciliation exists.

Conflicts return IdentityMembershipError with code CONFLICT. Invalid values use INVALID; missing references use MISSING_REFERENCE. Shared contracts check both repositories. Active family conflicts and changed-provenance duplicate active campaign relationships fail closed. The latter can be replaced only by explicit supersession followed by a new decision. Repositories validate entity and target existence, including the campaign's employer cluster. Employer resolution is not required.

Supersession and later insertion are separate explicit repository operations, not an automatic move workflow. A future application service can provide atomic replace semantics if such a workflow is authorized.

## Exact replay

A deterministic decision key includes owner, target, confidence, status, algorithm/version, evaluatedAt, sourceType and explanation. Membership ID and createdAt are recording identity/time, not decision provenance. Exact replay therefore returns the original record even when a caller retries with a new ID or recording timestamp. Reusing an existing ID for different decision content fails.

The key remains unique across history. Replaying a superseded decision returns its superseded record and never reactivates it. To make a new decision, supply new provenance (normally a new evaluatedAt) and a new ID. Replay is checked before family-preference restrictions, so a previously valid direct campaign decision still replays after its observation joins a family. New decisions remain blocked in that situation.

## Migration 8

The smallest additive migration for these entities creates:

- publication_families
- publication_family_memberships
- recruitment_campaigns
- recruitment_campaign_memberships

Membership foreign keys reference the actual identity entity and source_observations or publication_families as appropriate. Campaign employer_cluster_id references employer_clusters. ON DELETE RESTRICT preserves referenced history; no cascading deletion. No canonical_vacancy_id column, backfill, source rewrite or canonical rewrite is introduced.

Partial unique indexes enforce one active family per observation and one active relationship per campaign/target. Campaign indexes are per relationship, allowing several campaigns for the same target. A CHECK enforces target XOR. Status, confidence and explicit source types are constrained. decision_key is unique for replay. A BEFORE INSERT trigger enforces family preference even for direct SQL writes; no family-insertion trigger reconciles earlier direct decisions. Audit triggers permit only one-way supersession and prevent deletion. Reference/history/member indexes support targeted reads; query-plan tests verify indexed lookups.

Migration registration follows the existing transactional numbered migration mechanism. Upgrading a populated version-7 fixture preserves every old table's rows and the canonical vacancy projection. Running migration again is harmless.

## Repository and read foundation

PublicationFamilyRepository supports save, findById, findBySourceObservationId, findMembersByFamilyId, addMembership, findMembershipById, findMembershipHistoryBySourceObservationId, findActiveMembershipBySourceObservationId and supersedeMembership.

RecruitmentCampaignRepository supports save, findById, findByEmployerClusterId, findByTarget, findMembersByCampaignId, addMembership, findMembershipById, findMembershipHistoryByTarget, findActiveMembershipsByTarget and supersedeMembership.

Member lists and identity lookups expose active decisions only. Dedicated history and membership-ID lookups retain proposals, rejections and superseded decisions. Membership order is evaluatedAt ascending then ID ascending; campaign entity lists use ID ascending. findByTarget reads only explicitly persisted target relationships. It does not implicitly project an observation through its family or manufacture campaign links.

SQLite repositories use indexed, targeted queries and immediate transactions for validating and inserting decisions. In-memory repositories validate references through their supplied observation/employer/family stores and apply the same replay, conflict, order and lifecycle rules. The in-memory campaign repository uses the same family instance and a synchronous final active-family check after asynchronous reference reads. Concurrent family assignments are covered by the shared contracts.

No application service was needed: repository actions provide the explicit foundation. No capture adapter, provider matching rule, acquisition assignment, review DTO, HTTP endpoint or production UI was changed. M12.7 family/campaign fields remain absent until a later read-model milestone.
