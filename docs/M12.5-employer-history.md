# M12.5 — Employer-centric vacancy history

Baseline: `afdc89dcd675297c90bcc80066b6d9c0409c16ee`. No commit and no migration.

## Architecture and reused components

The review response now exposes optional `employerHistory`, using the existing `EmployerMemoryView` rather than introducing a second vacancy/history DTO. `getEmployerMemoryView`, `EmployerMemoryPublicDataSource`, existing interaction events and their ordering rules, and M12.4 alias evidence are reused. The view adds cluster display label, active known names, contact/offer/withdrawal flags and counts, and provider names.

`GET /vacancies/:canonicalVacancyId/review` returns this in the existing single review read. Action responses naturally refresh it through the same workflow. No new endpoint, source writes, interaction types, identity decisions, or assignment lifecycle changes were added.

## Membership and current-vacancy exclusion

SQLite history lookup now follows effective ACCEPTED/USER_CONFIRMED assignments, including private confirmations that have not rewritten the canonical source projection. It uses the same precedence as current review: the first human-confirmed assignment in canonical source order, otherwise the last effective automatic assignment in that order. Rejected, proposed, and superseded assignments do not establish membership. Only when there are no effective assignments does the existing single explicit EMPLOYER cluster relationship provide a fallback; ambiguous fallback relationships are excluded.

Names alone never establish history membership. An ACTUA vacancy for another client cannot enter HEUFT history by sharing its recruiter, displayed name, or alias spelling. Alias-linked/propagated vacancies appear together because their effective assignments share a cluster.

The current canonical vacancy is removed before interaction retrieval and aggregation. Every other canonical vacancy counts once, regardless of observation count. The legacy employer booleans and previous-history signals now also exclude the current vacancy. Current-vacancy interaction controls retain their existing meaning.

## Summary and interaction semantics

- `summary.vacancyCount` is the number of previous distinct canonical vacancies.
- `everAppliedCount`, `everContactedCount`, `everInterviewedCount`, `everOfferedCount`, `everRejectedCount`, and `everWithdrawnCount` each count vacancies with at least one matching event, not events. Outcomes may overlap for one vacancy.
- Per-vacancy flags remain true after later events, while `currentUserState` follows the latest event by occurredAt, then recordedAt, then event ID using the existing comparator.
- `lastUserInteractionAt` and employer `summary.latestUserInteractionAt` use event occurrence timestamps only. No interaction means null, never a capture timestamp.
- Previous roles retain title and location; SQLite additionally supplies distinct provider names. Ordering retains the existing newest observed vacancy first, then canonical ID ascending; missing observation times come last. All other canonical vacancies qualify, not just those captured before the current vacancy.

## Aliases, safety, and privacy

Known names start with the cluster display label, then active explicit aliases in evidence creation/ID order. Existing organization-name normalization deduplicates them, preserving the first original human-readable spelling. An alias remains active only while its supporting matching USER_CONFIRMED assignment is effective. Superseded evidence stays in the repository audit history and is excluded from normal known names. Historical displayed names remain separate observed relationships and are never promoted into aliases.

Authoritative current-employer history is omitted for missing, UNRESOLVED, and CONFLICTED identity. PROBABLY_RESOLVED and RESOLVED clusters qualify without requiring legal identity for the former. Pending employer-memory and named-client candidates remain candidates; their potential history is not presented as current-employer history. Recognition and review eligibility were not changed.

The read model combines public vacancy facts and private history without persisting that combination. The integration test snapshots source facts, assignments, aliases, and interactions to verify the HTTP read is non-mutating.

## UI

The compact Employer history section shows employer identity, previous-vacancy/application/interview/offer/rejection counts, last interaction, linked previous roles, locations/providers, latest states and historical outcome labels, and known names. Current recruiter/staffing names appear separately as “Current vacancy via”. Newly known employers show “No previous vacancies with this employer.” Conflicted identities retain an explicit review message. Existing confirmation, ambiguity and named-client controls remain in place. The previous full alias-audit panel was replaced by active known names.

## Queries

The existing SQLite provider starts from target-cluster assignment/relationship indexes, resolves each candidate canonical membership, then reads selected vacancy facts and relationships in two queries. Relationship grouping uses a map. Both interaction repositories support a batch lookup; SQLite uses one parameterized JSON ID list, avoiding a query per historical vacancy and parameter-count limits. Legacy/custom repositories without batch support retain a compatibility fallback. Both alias repositories now expose `findActiveByClusterId`; SQLite joins evidence to effective human assignments using existing indexes. No schema/index changes were necessary.

## Remaining considerations for M12.6

No required M12.5 work is deferred. Very large employer histories may eventually warrant pagination; the current read returns all previous vacancies. Candidate-specific history remains an optional future enhancement. Effective-assignment precedence is intentionally unchanged and represented in both application selection and SQL, with parity tests; future changes to that policy must update both. Full alias audit remains available internally. No ranking, automation, notes, external enrichment, fuzzy matching, or cluster merging is introduced.
