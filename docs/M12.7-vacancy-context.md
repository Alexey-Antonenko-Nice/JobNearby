# M12.7 — Vacancy context across sources

Implemented against baseline `4c5fe36a95fb64f48eed9197ec0afd24d73944be`, with the approved reduced scope. No migration, matching rule, persistence of derived context, or commit.

## Architecture and API

`VacancyReviewView.vacancyContext` is a required, compact derived object assembled by `getVacancyReviewView`. `deriveVacancyContext` combines public observations already belonging to the canonical vacancy with its private interaction events. Existing GET review and action responses serialize it automatically; Date values become ISO strings and unknown values remain null. Existing review signals and user state remain available. The UI accepts the field optionally for compatibility with older responses.

The context does not depend on EmployerCluster resolution. An unresolved employer still receives vacancy context. Employer assignment/alias/memory review rejection is never interpreted as a job rejection.

## Exact semantics

- `currentCanonicalVacancyId`: the canonical ID requested by review.
- `observationCount`: number of distinct immutable SourceObservation IDs in that canonical vacancy's persisted membership. Reprocessing or recapturing the same snapshot does not create another sighting. Capture occurrences are not counted.
- `seenBefore`: true precisely when observationCount is greater than one. The current review route supplies only canonicalVacancyId; this is a multiplicity fallback, not an assertion about observations preceding a particular current observation. One old observation alone remains false.
- `currentSourceObservationId` and `currentSourceProvider`: null. Neither the first nor latest provider is invented as the current source. Exact current-observation exclusion is inapplicable to the existing route and deferred until a real observation-aware review entry point exists.
- `sourceProviders`: unique provider IDs using the existing `normalizeVacancyProviderNamespace` function (trim, collapse whitespace, lowercase), sorted in deterministic string order. No friendly aliases or new provider equivalence rules.
- `sourceCount`: length of sourceProviders. Three observations from Indeed are three observations and one source.
- `firstSeenAt` / `lastSeenAt`: minimum/maximum `SourceObservation.observedAt` (SQLite `source_observations.observed_at`), the field already used for review's latestObservedAt. Neither publication dates, capture occurrence dates, interaction dates nor employer-memory dates are used. Empty observations produce null dates.
- All nine `*Before` action flags mean that an existing private UserVacancyInteraction event of the corresponding type exists for this canonical ID. They describe history, not a new state machine. INTERVIEW maps to interviewedBefore and OFFER to offeredBefore. Only interaction REJECTED sets rejectedBefore. Other canonical vacancies' actions never set these flags.
- `latestInteractionType` / `latestInteractionAt`: latest event by the existing occurredAt, recordedAt, event-ID comparator. latestInteractionAt is that event's occurredAt. No interactions means both null. Chronology takes precedence over lifecycle assumptions.

## Application provenance

The model already permits APPLIED.metadata.sourceObservationId. `appliedViaProvider` and `appliedViaSourceObservationId` describe the latest APPLIED event under the same chronological comparator. They are populated only when its reference resolves to an observation in the current canonical vacancy's persisted membership. This uses the loaded membership observations and requires no additional query. Missing, dangling or unrelated references produce null provenance while appliedBefore remains true. If the latest application lacks provenance, an older application's provenance is not borrowed. A newer non-APPLIED action does not remove the latest application's recorded provenance.

The UI labels this specifically as "Latest application via". Current review action buttons do not provide sourceObservationId, so actions recorded there do not acquire inferred provenance. A future observation-aware application entry point may supply it explicitly.

## Deferred identity layers

PublicationFamily and RecruitmentCampaign currently exist only in design documentation. This milestone adds no models, repositories, tables, membership inference, fake placeholders, or runtime fields for them. Their relationship tests are not applicable to the approved scope.

Same canonical vacancy means shared canonical identity. A future publication family may relate different canonical vacancies representing related publications. A future recruitment campaign may relate distinct vacancies in a hiring campaign. Neither relationship should mean the current canonical vacancy was seen or acted on. Employer history is also separate from all three.

## Queries and UI

SourceObservationRepository gains an optional findByIds capability. SQLite implements one targeted query using json_each of member IDs, and the in-memory repository implements a matching batch read. Review deduplicates membership IDs, uses the batch capability in production, checks every referenced observation exists, and retains a findById fallback for existing minimal adapters. The existing one-canonical interaction history query is reused; the derivation performs no interaction writes or queries. No per-related-vacancy queries are introduced.

Review displays a compact Vacancy context section with seen-before status, providers, source and observation counts, first/last seen, historical action labels, latest action and supported application provenance. A one-observation vacancy reads "First time seen" and no interactions reads "No prior actions". No recommendation or duplicate label is added.
