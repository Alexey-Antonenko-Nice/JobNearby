# M12.6 — Employer action context / prior outcome signal

Baseline: `348ce16fda96dd41f74d7650bf146f3b22bc8501`. No commit, migration, or persisted context.

## Architecture and M12.5 reuse

The flow is `getEmployerMemoryView` → `deriveEmployerActionContext` → the existing `VacancyReviewView`. The pure derivation helper consumes M12.5's previous-only employer history. It has no repositories, additional queries, or identity inference.

The existing batch-loaded interaction loop additionally selects the latest APPLIED occurrence and latest interaction event. `EmployerMemoryView.summary` gains `latestApplicationAt` and `latestUserInteractionType`; its existing `latestUserInteractionAt` is now projected from that same selected event. Counts, effective cluster membership, aliases, and current-vacancy exclusion all reuse M12.5.

## Exact semantics

- `knownEmployer` is true whenever authoritative PROBABLY_RESOLVED/RESOLVED history is available, even with zero previous vacancies. This intentionally differs from existing `knownBefore`, which means a previous vacancy exists.
- All six counts count distinct prior canonical vacancies with at least one corresponding interaction event. Repeated events and source observations do not increment a count again. Every `...Before` boolean equals its count > 0.
- `lastApplicationAt` is the maximum occurredAt of prior APPLIED events. It never uses capture, publication, or recording time.
- `lastInteractionAt` and `lastInteractionType` come from the same latest prior event, selected using the existing occurredAt, recordedAt, event-ID comparator. Event types have no precedence. Timestamps are absolute Date values serialized as ISO strings; absent dates/type are null.
- CONTACTED, INTERVIEW, OFFER, REJECTED, and WITHDRAWN each require their own explicit interaction event. No progression or sentiment is inferred. CLOSED can be the latest neutral interaction and does not imply rejection or withdrawal.
- Assignment REJECTED from employer-memory, alias, or named-client review never contributes to job rejection. Only the private vacancy interaction REJECTED contributes.
- Current canonical vacancy events are excluded before counts and event selection. Its action controls remain independent; a newly recorded current action can contribute when reviewing a different vacancy for that employer.

## Identity and provenance safety

M12.5 effective employer-cluster membership is unchanged. Alias-linked Air Products/Air Products S.A.S. vacancies share context through the cluster, with no alias-specific action rules. ACTUA and other intermediary names do not establish membership, so unrelated clients' interactions cannot contribute to HEUFT context.

Missing, UNRESOLVED, and CONFLICTED employers have no authoritative action-context property. Pending M12.2 ambiguity and M12.3 named-client candidates do not create context. Existing confirmation and recognition policies are unchanged; no candidate-specific action history is introduced.

Source/canonical facts and private event history remain unchanged by reads. The new context is a projection only. Existing HTTP read snapshot coverage verifies that it does not mutate source, canonical, assignment, alias, or interaction rows.

## API, UI, and performance

`GET /vacancies/:canonicalVacancyId/review` now includes optional `employerActionContext` with all requested booleans/counts and last application/interaction fields. No endpoint is added. Existing action responses obtain refreshed context from the same review workflow. Integration coverage checks ISO serialization and current-action exclusion.

A compact Employer context group within Employer history shows six factual Yes/count or No rows plus the last application and latest interaction. It replaces the overlapping count summary when present; previous roles, aliases and recruitment context remain available. Known employers without interactions show “No previous applications or interactions with this employer.” Unresolved identities show no misleading zero-valued context. Date formatting stays in the UI. No recommendation, score, ranking, cooldown, or automation is introduced.

There are no new database queries or repository changes. Additional event selection is linear in the already-loaded batch; the context helper is constant-time over its summary. A workflow spy test checks one prior-history batch and only the existing current-vacancy history read during GET.
