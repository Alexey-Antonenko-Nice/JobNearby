## Architecture and compatibility

The vacancy review model now has a generalized `employerReview` with discriminated `CONFIRMED_MEMORY` and `NAMED_CLIENT` candidates. The existing `employerMemoryReview` field remains a compatibility projection of memory candidates only. It is not separate persisted state. Existing M12.2 discovery and decision semantics are retained, and memory review takes precedence over named-client review.

Named-client candidates are derived from canonical organization relationships and their evidence references. Reads do not create clusters, assignments or review records. A narrow atomic decision operation was added to the existing employer recognition persistence interface and implemented for both in-memory and SQLite persistence.

## Exact eligibility and suppression

A named-client candidate requires all of the following:

- Exactly one distinct normalized CLIENT name. Duplicate relationships for that same name are permitted; any unnamed/unusable CLIENT or multiple distinct names fails closed.
- An existing effective ACCEPTED assignment on the latest observation to an anonymous UNRESOLVED cluster. Every other effective/referenced employer cluster on the vacancy must also remain anonymous and UNRESOLVED. This existing membership is the durable audit anchor for rejection.
- No effective USER_CONFIRMED assignment on any source observation of the vacancy.
- No differently named explicit EMPLOYER relationship.
- No same-normalized-name RECRUITER, STAFFING_AGENCY or CONSULTANCY classification for the client.
- A displayed organization that also has a recruiter/staffing/consultancy role, establishing the intermediary context.
- At least one CLIENT relationship with confidence at least 0.98, backed by an ORGANIZATION_EVIDENCE reference belonging to a current source observation. Raw text is not independently re-parsed by review discovery.
- No prior rejection for this vacancy and normalized client name.
- No CONFLICTED same-name historical cluster and no ambiguity between multiple suitable named clusters.

Name checks reuse organization evidence normalization and the existing explicit-extraction name-usability function. Additional fail-closed checks reject generic client/company phrases, trailing grammatical connectors, numeric-only values, exact canonical location values and single-word non-acronym names. No name is fuzzily repaired. These conservative checks can withhold legitimate names; they do not assert that withheld names are not employers.

## Cluster reuse and creation

An exact normalized-name PROBABLY_RESOLVED or RESOLVED cluster is reused when it is the unique suitable match. Available effective historical USER_CONFIRMED observation counts are exposed as supporting context; CLIENT memory never triggers M12.1 automatic propagation.

If no suitable cluster exists, confirmation creates a minimal PROBABLY_RESOLVED cluster with the client display name. It has no fabricated resolvedEmployerId. An already stronger reused cluster is unchanged. Multiple suitable matches fail closed rather than selecting a winner or creating another same-name cluster.

## Human decisions and idempotence

CONFIRM records USER_CONFIRMED and supersedes the latest anonymous ACCEPTED assignment atomically with any required cluster creation. Existing assignment history and historical confirmations are retained. The candidate token binds the vacancy, normalized client name, current observation/assignment, supporting evidence IDs and reusable cluster ID; new decisions revalidate eligibility and that token.

REJECT appends a REJECTED assignment against the existing unresolved cluster. Its algorithm is `user-named-client-employer-review`; its explanation stores the candidate token, client name, source relationship, decision and human-readable explanation. It does not pretend that the unresolved cluster identifies the client. REJECTED rows are excluded by the existing effective-membership queries, so the ACCEPTED unresolved assignment remains effective. No named cluster is needed merely to reject a suggestion.

A deterministic decision ID per vacancy/normalized client name makes repeat decisions converge and preserves rejection across subsequent reads and database restart. Repeated identical decisions return the current review without duplicate writes. Opposite decisions for the same completed suggestion fail with 409. Both repository implementations are tested for concurrent retries; competing confirm/reject decisions have one winner, and failed confirmation rolls back any new cluster.

## ACTUA/HEUFT and source preservation

The integration test starts with explicit text extraction and canonicalization of the ACTUA/HEUFT case. The review offers HEUFT France as NAMED_CLIENT and keeps the generic ACTUA confirmationCandidate null. HEUFT's existing confirmed history is useful context but never enough for automatic client promotion.

Confirmation makes HEUFT the private effective employer. Rejection keeps the private effective employer unresolved. Both actions preserve source observations, canonical vacancy data, evidence references and organization relationships:

- DISPLAYED_COMPANY: ACTUA SAVERNE
- RECRUITER: ACTUA Saverne
- CLIENT: HEUFT France

The canonical unresolved employer reference is also preserved; the review derives current membership from assignment history. CLIENT is never rewritten to EMPLOYER.

## API and UI

GET `/vacancies/:id/review` adds optional `employerReview: { required: true, candidates }`. NAMED_CLIENT data includes name, type, candidateId, sourceRelationship, canonicalVacancyId, sourceObservationIds, supportingEvidenceIds, explanation, deterministic reasonCode `NAMED_CLIENT_POSSIBLE_EMPLOYER`, optional-existing cluster identity/status (null when absent), and priorConfirmationCount. Counts are confirmed observations, not asserted counts of distinct canonical vacancies.

POST `/vacancies/:id/employer-review` accepts either:

- `{ type: "NAMED_CLIENT", candidateId, decision: "CONFIRM" | "REJECT" }`
- `{ type: "CONFIRMED_MEMORY", employerClusterId, decision: "CONFIRM" | "REJECT" }`

Malformed or unsupported fields return 400. Stale/non-candidate decisions return 409. Successful decisions return the updated review. The existing `/employer-memory-review` endpoint remains available with its original payload and behavior.

Vacancy Review adds a minimal “Possible employer” section showing HEUFT, its CLIENT source relationship, explanation, optional confirmation count and “Confirm employer” / “Not the employer” actions. Existing pending/error handling is reused. ACTUA has no employer-confirm button. No inbox redesign or modal was added.
