# M12.2 — Employer Memory Ambiguity Review

Baseline: `47954565e635e54e568b7786fea54e7876e5d445`. No commit or migration.

## Behavior

Candidates require an exact match under the existing organization-evidence normalization and effective historical USER_CONFIRMED assignments from observations outside the current vacancy. Case, Unicode normalization, spacing and hyphen normalization are reused; no fuzzy matching, aliases, inference or web lookup was added.

Review is generated when compatible confirmed memory exists and at least one condition holds:

- Multiple confirmed clusters match the same normalized current employer/displayed-company name.
- Multiple distinct normalized current employer/displayed-company names exist. A candidate must still agree with every explicit EMPLOYER name.
- A current named non-final assignment points to a different cluster, or current cluster state is CONFLICTED.
- An existing recognition proposal marks the observation as requiring review.

A single compatible remembered employer retains M12.1 automatic propagation and produces no memory-review panel. An existing same-cluster, named non-final assignment does not manufacture a conflict.

## Suppression and safety

STAFFING_AGENCY, RECRUITER, CLIENT or CONSULTANCY evidence suppresses all memory candidates, including same-name staffing/recruiter organizations. Explicit incompatible EMPLOYER evidence suppresses a candidate. Historical CONFLICTED clusters, anonymous labels, ACCEPTED-only and PROPOSED-only history are excluded. Current USER_CONFIRMED assignments and current PROBABLY_RESOLVED or RESOLVED clusters are protected; missing referenced current clusters fail closed.

All existing provider tests passed in the complete backend suite, including the controls for Randstad, LHH, ManpowerGroup, Actual, SATIS, MécanoJob, Free-Work, LinkedIn CEA, Indeed/Workday Air Products, Daimler and Bürkert. These are fixture/regression results, not live provider checks.

## Candidate state and decisions

Candidate state is derived, deduplicated by cluster ID and sorted deterministically by cluster ID. Reads do not create proposals or assignments. Multiple matching clusters have no arbitrary winner: processing bypasses generic matching and retains the existing unresolved-cluster fallback. The review read model exposes `required: true` and all eligible candidates.

REJECT stores a non-effective REJECTED assignment using `user-employer-memory-review`, preserving history. All source observations of the current vacancy are checked for rejections, so adding an observation does not reintroduce the candidate. Rejection IDs are deterministic per vacancy/cluster, making concurrent retries converge. Rejected memory also cannot return through the generic same-name employer confirmation prompt.

CONFIRM reuses the selected existing cluster and creates USER_CONFIRMED on the latest observation, superseding its automatic effective assignment when necessary through the existing atomic repository operation. Cluster status and resolvedEmployerId are not changed, no duplicate cluster is created, and prior confirmations remain intact. Candidate eligibility is checked before a new decision. Sequential and concurrent identical decisions are idempotent; a different candidate cannot override the completed human confirmation.

## API, read model and UI

GET `/vacancies/:canonicalVacancyId/review` adds optional `employerMemoryReview: { required: true, candidates }`. It is omitted when no candidates remain. Candidate data includes employerClusterId, displayLabel, status, currentOrganizationName, deterministic reasonCodes, explanation, priorConfirmationExists and priorConfirmationCount. The count measures confirmed source observations, not distinct canonical vacancies, and the UI labels it accordingly.

POST `/vacancies/:canonicalVacancyId/employer-memory-review` accepts `{ employerClusterId, decision: "CONFIRM" | "REJECT" }` and returns the updated review. Invalid payloads return 400; stale/non-candidate decisions return 409; missing vacancies return 404.

Vacancy Review adds a small “Possible known employer” section with the label, status, confirmation count, explanation, “Confirm employer” and “Not this employer” buttons. Actions reuse the existing pending/error behavior. The ordinary confirmation button is suppressed during memory review and for rejected same-name memory. No inbox redesign or modal was added.

## Remaining limitations

No blocker. Discovery retains the existing repository's full-cluster scan, once per discovery call, then applies exact evidence normalization. This avoids the repository hint filter's different punctuation/spacing semantics; it does not add an index or schema. Counts summarize confirmed observations only. No cluster merge, legal-entity resolution, reconsider-rejection workflow or cross-process canonical-vacancy locking was introduced; effective assignment replacement uses existing repository concurrency controls.
