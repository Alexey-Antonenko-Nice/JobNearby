# M12.9 - Publication and campaign context in vacancy review

Baseline: `5e6dad11c5673919e19fe099ee3f607227f9dfad`. Read-only integration. No migration, membership mutation, identity inference, or commit. The application database was not opened during implementation; tests used in-memory or temporary databases.

## Architecture and traversal

The existing VacancyContext is extended with publicationFamilies and recruitmentCampaigns arrays. getVacancyReviewView passes the canonical vacancy's persisted observation IDs to a dedicated PublicationCampaignContextSource. This follows the existing public read-source pattern used by employer memory. Production review wiring supplies the SQLite source; an equivalent in-memory source is available for tests and in-memory compositions. Minimal legacy compositions without the optional source return empty relationship arrays.

Traversal is limited to explicit active relationships:

1. Canonical vacancy's original observation IDs -> active family memberships.
2. Distinct family IDs -> family entities and all active member observations.
3. Those family IDs -> active family-target campaign memberships.
4. Original observation IDs -> active direct campaign memberships.
5. Distinct campaign IDs -> persisted campaign entities.

Direct campaign links on other observations in the family are not followed. No employer, title, URL, location or provider similarity is used. CanonicalVacancy never becomes a direct membership target. Existing M12.8 persistence remains unchanged.

A shared pure projection, derivePublicationCampaignContext, constructs both adapters' results. New context contains only public identity information. It makes no interaction queries and writes no derived data.

## Multiple identities, deduplication and evidence

An observation has at most one active family, but a canonical vacancy can reach multiple families through different observations. All reached families are retained once each, sorted by ID. No authoritative family is arbitrarily selected.

Multiple campaigns are valid. Each campaign appears once, sorted by ID, while every distinct membership path remains present. Path types are PUBLICATION_FAMILY and DIRECT_OBSERVATION. A direct membership that remains active after its observation joins a family stays visible, including when the same campaign is also reached through one or more families. Membership records are deduplicated by persisted membership ID, not by provider or apparent similarity.

Family membershipEvidence covers all active member observations used in the family summary. Each record preserves membership ID, family/observation target IDs, membership status, confidence, sourceType, algorithm/version, evaluatedAt, createdAt and optional explanation. Campaign paths preserve the analogous evidence and the exact target. No confidence aggregation or new score is calculated.

Active uses M12.8's ACCEPTED or USER_CONFIRMED status with no supersededAt. PROPOSED, REJECTED and superseded decisions do not establish relationships or contribute to family totals. Campaign entity status is separate: an ENDED campaign is displayed if its membership decision is still active.

Evidence paths are sorted by evaluatedAt, then membership ID, using the existing M12.8 comparator. Provider names and current observation IDs use deterministic sorted order.

## Counts, timestamps and providers

Family observationCount is the number of distinct active observations across the whole family, including observations belonging to other canonical vacancies. currentVacancyObservationIds and currentVacancyObservationCount identify only the original review vacancy's subset. Family totals never modify M12.7's canonical observationCount or sourceCount.

Family firstSeenAt and lastSeenAt are the minimum and maximum member SourceObservation.observedAt. Family creation/update dates and publication dates are not substituted. Providers come from these actual member observations, normalized with M12.7's normalizeVacancyProviderNamespace, deduplicated and sorted. No new provider alias mapping is introduced.

Campaign firstObservedAt and lastObservedAt remain the campaign entity's persisted fields, not derived family observation extrema. The UI labels them as campaign timestamps. No campaign vacancy count or sum of family and observation targets is invented.

## Employer and interaction isolation

Each campaign retains its own persisted employerClusterId. It does not confirm or replace the current vacancy's employer. Unresolved and conflicted current employer clusters do not suppress publication/campaign context. No employer-name lookup or inference was added; the compact UI omits employer labels rather than guessing. The employer cluster ID remains available in the response.

Current vacancy action flags continue to derive exclusively from private events on that canonical vacancy. An APPLIED event on another canonical vacancy in the same family does not set current.appliedBefore. Employer history and employer-review rejection behavior are unchanged. Related-action aggregation is deliberately absent.

## Missing data

No persisted relationships produces two empty arrays. The UI omits the section in that case; it does not assert that no real-world relationships exist.

A referenced family, campaign or active member observation missing from the snapshot raises an explicit error, following existing review behavior for missing observation references. It does not fabricate dates, silently reduce counts or return a misleading partial summary. Valid SQLite foreign keys normally prevent this condition.

## Query changes and consistency

No schema changes or new repository writes. SqlitePublicationCampaignContextSource reuses the existing SqliteMembershipLedger decoder and active predicate. It performs at most six targeted batched SELECT statements using existing ID/target indexes and JSON ID sets, regardless of the number of families, observations or campaigns. A UNION of indexed family-target and direct-observation membership queries retains both paths without per-entity queries. Only the minimal observation fields needed for family summaries are loaded. Private event loading is reused from the existing review flow.

All new SQLite reads run synchronously inside one deferred read transaction. A two-connection WAL test proves that a concurrent membership supersession does not mix snapshots: the current response retains the old count, and the next read sees the change. This does not redesign transaction ownership for the whole review: the canonical observation IDs are loaded by the existing review flow before the context snapshot, and private/employer portions retain their existing transaction boundaries.

In-memory family/campaign repositories gain synchronous readContextMemberships methods, returning copied batch snapshots. The in-memory context source takes both membership snapshots without yielding, then loads immutable observations in one existing findByIds call. Both adapters use the same projection, and full review results are checked for parity.

## Read model, API and UI

VacancyContext now extends PublicationCampaignContext. The existing derivation initializes empty arrays and review overlays the persisted traversal result. Existing M12.7 scalar fields and action semantics stay unchanged.

GET /vacancies/:canonicalVacancyId/review includes the arrays through existing serialization. Dates serialize to ISO strings. Action responses returning a refreshed review include the same context. No new endpoint or mutation control was introduced. HTTP tests use actual SQLite repositories and compare database changes before/after GET; the read is mutation-free. Action tests verify public identity rows remain unchanged.

The new compact Publication and campaign context section shows distinct family/campaign counts, family title or ID, actual providers, family observation total and current-vacancy subset, family seen dates, campaign status and timestamps, and family/direct path wording. Campaigns display once even with multiple paths. Technical provenance remains available in the API rather than crowding the UI. No duplicates, application implication, score, recommendation or hiring-likelihood claim is added.

The UI's new context types reuse serialized domain types so their structures stay aligned. Rendering tolerates older responses missing the arrays.

## Limits and recommended M12.10

Campaign-wide member counts, campaign employer display labels, navigable relationship details, related-action aggregation and membership editing are not implemented. No global review snapshot was introduced beyond the coherent public relationship read. SQLite rereads minimal family observation facts within that transaction; M12.7's original observations and interaction processing remain unchanged.

Recommended M12.10: a read-only relationship detail view that exposes persisted evidence and source observation links with clear lifecycle labels. Any related-action aggregation or explicit membership editing should receive its own approved semantics and scope; neither should be inferred from this milestone.
