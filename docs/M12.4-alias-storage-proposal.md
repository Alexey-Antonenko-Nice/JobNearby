# M12.4 — Alias evidence storage proposal (approval required)

Baseline verified: `e900f391d1b0a2a0b9ad3e680462732b15ac4c34`.

Status: approved and implemented. Migration 007 and the additive alias-evidence repositories/application integration are present; no commit has been made.

## 1. Why a dedicated table is recommended

`employer_clusters` has a display label, status, timestamps, location hint and optional resolved employer ID. There is no alias collection or extensible metadata field.

`observation_cluster_assignments` describes membership of one observation in one cluster. Its effective-membership constraints and `superseded_at` describe assignment lifecycle, not independent name-equivalence evidence. Source/canonical organization names must remain untouched.

Assignment `explanation` can technically carry JSON, as the M12.3 decision audit already does. A no-migration implementation is therefore technically possible, but would make free-text assignment explanations the authoritative, cross-vacancy alias registry. It would need new conventions for alias identity, provenance, uniqueness, lookup and supersession, none of which the current schema enforces. Parsing arbitrary historical confirmation explanations or assuming every displayed name on a confirmed vacancy was confirmed as equivalent would also be unsafe.

I recommend first-class alias evidence instead of extending that audit-payload convention into a reusable identity store. This is an architectural recommendation, not a claim that SQLite cannot store alias JSON in the existing explanation column.

## 2. Proposed minimal schema

One additive table: `employer_alias_evidence`.

| Column | Purpose |
| --- | --- |
| `id` TEXT PRIMARY KEY | Evidence identity |
| `alias_name` TEXT NOT NULL | Original name explicitly confirmed by the user |
| `normalized_alias_name` TEXT NOT NULL | Existing organization normalization; no suffix stripping |
| `employer_cluster_id` TEXT NOT NULL | Foreign key to employer_clusters |
| `source_type` TEXT NOT NULL | Initial supported value: USER_CONFIRMED_ALIAS |
| `source_assignment_id` TEXT NOT NULL | Foreign key to the supporting USER_CONFIRMED assignment |
| `created_at` TEXT NOT NULL | Time of the equivalence confirmation |
| `explanation` TEXT NOT NULL | Human-readable evidence explanation |

Proposed constraints and indexes:

- Nonempty names and explanation; supported source type checked.
- UNIQUE `(employer_cluster_id, normalized_alias_name, source_assignment_id)` prevents duplicate evidence on retries.
- An index on `(normalized_alias_name, employer_cluster_id)` supports direct lookup.
- The unique index above also supports cluster-first history lookup.
- **No global uniqueness on normalized_alias_name:** evidence may point to different clusters, and that conflict must produce ambiguity rather than discarding evidence or selecting a winner.
- Source observation provenance is retrieved through source_assignment_id, avoiding a redundant observation foreign key that could disagree with the assignment.

Application validation must establish that the supporting assignment is USER_CONFIRMED and targets the same cluster. Initial lookup should require that supporting confirmation remains effective, so a superseded employer decision cannot silently continue authorizing automatic alias reuse. The evidence row remains preserved for audit.

Initial scope is USER_CONFIRMED_ALIAS only. The human selection of an existing cluster for a differently named current employer/client is the explicit proof. No automatic backfill of SAME_CONFIRMED_EMPLOYER_CLUSTER evidence from ambiguous old display names or free-text explanations is proposed.

## 3. Migration impact

Proposed migration 007 would create only this table and its indexes and register it with the existing migration runner. It would not alter existing tables, rewrite names, change employer status or assign legal identity.

There would be no historical backfill. The table starts empty; old recognition behavior remains unchanged until a user explicitly creates evidence. The migration would run transactionally under the existing migration mechanism.

Migration 007 has been created and is applied by the existing forward-only migration runner. It creates an empty table; no historical backfill is performed.

## 4. Repository and application changes after approval

Add an alias-evidence domain type and in-memory/SQLite repositories with narrow operations such as:

- save alias evidence idempotently;
- find evidence/target clusters by normalized alias;
- find evidence by employer cluster.

Extend the existing atomic employer-review persistence operation to store the explicit human assignment and alias evidence together when both are newly created. Reject/keep-separate decisions can retain the existing append-only REJECTED assignment semantics, scoped to the current vacancy and selected target; they do not create a global anti-alias.

Recognition would compare normalized display labels first, then query explicit alias evidence for additional identity support. A cross-cluster conflict, including exact-label versus alias evidence, must not be hidden by lookup ordering. Results are deduplicated by cluster and ordered deterministically.

- M12.1: one safe historically confirmed target may be reused as ACCEPTED, algorithm confirmed-employer-memory.
- M12.2: multiple targets require ambiguity review; no arbitrary winner.
- M12.3: alias-linked CLIENT targets remain human-review candidates only.
- Existing recruiter/staffing/client and explicit-employer contradiction checks remain authoritative. Alias evidence cannot override them.
- Case-only normalized equivalence creates no alias evidence. Legal suffix difference alone creates no evidence.

The minimal UI would let a user explicitly select an existing confirmed employer and choose “Same employer” or “Keep separate.” It would not manufacture similarity-based suggestions. Existing generalized employer review is the intended integration point; legacy review APIs remain compatible.

## 5. Rollback and compatibility

Older application code does not access the new table and can continue operating with it present. Existing assignments and source names retain their current representation.

An application rollback should leave the additive table intact so alias audit evidence is not lost. Older code would ignore alias evidence, so future alias-based recognition would stop, while previously recorded assignments remain intact.

The current migration runner supports forward migrations only. Physically removing the table would be a separate explicit, data-destructive operation: it would discard alias evidence but would not undo previously propagated assignments. No automatic down migration or assignment-history rewrite is proposed.
